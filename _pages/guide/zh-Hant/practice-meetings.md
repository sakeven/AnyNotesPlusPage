# 會議記錄與追蹤

開會時想認真聽，又怕漏掉結論，常常只能一邊說、一邊趕著記。等到散會，筆記里留下了不少話，卻不一定看得出哪些已經定了、哪些只是提議。

下面以一次發佈前的專案討論為例。團隊要確定本次發佈範圍，還有測試和幫助文檔沒安排完。用 AnyNotes 錄下討論，會後核對結論，再把明確的任務設為提醒。

## 會前準備：議程和上次的結論

如果是一個會持續推進的專案，先建好[主題]({{ "/zh-Hant/guide/topics/" | relative_url }})，放入議程、上次的結論和這次要看的資料，再從主題里開始錄音。以後補充的材料也放在這裡，下次開會就不用重新翻找背景。

只有一次的短討論，也可以直接從首頁錄音，不必為了記一場會先建立一套分類。先把內容留下來，之後再決定要不要歸入主題。

## 錄音時，隨時看要點和轉寫內容

開始[錄音]({{ "/zh-Hant/guide/recording/" | relative_url }})後，照常討論。iOS 的 API Key 模式可以邊錄邊看「即時整理」：現在主要在談什麼，還有哪些問題沒有說清楚，接下來可能要做什麼。需要核對一句話時，再切到「轉寫內容」。

討論卡住時可以點「幫我想想」。例如大家已經說了幾個方案，卻一直沒有判斷標準，可以借助建議補問一句：“這次最在意的是時間、預算，還是結果的完整程度？”不需要每出現一條建議就打斷大家。

錄音中的整理適合幫你跟上討論，不宜直接當成最終會議記錄。後面有人改口、補充或否定了一個方案，結論也可能跟著變化。

## 散會後，先分清「定了」和「還沒定」

點擊「完成」儲存，等完整錄音轉寫和整理結束，再打開筆記。先看結論，遇到日期、金額、名字或聽起來不太確定的地方，回到原文核對。

接著從筆記進入「深入探討」，讓 AI 按你要發出去的形式整理。可以直接這樣說：

> 幫我整理一份可以發給參會人的會議記錄。先寫這次已經定下來的事，再列行動項，最後放還沒定的問題。負責人和時間只用原話里明確說過的內容；沒有說清楚的寫「待確認」。提議過但最後沒採用的方案，不要寫成決定。

讀結果時，尤其留意這三種說法：

| 討論里說的是 | 會議記錄里應該怎樣處理 |
| --- | --- |
| “這個方案可以考慮” | 留作候選方案，還沒有決定 |
| “我週五前確認一下” | 記錄確認任務，核對說話人和具體日期 |
| “這件事需要有人跟進” | 保留任務，但負責人仍待確認 |

發出會議記錄前，把「待確認」的幾處問清楚。比如截圖中的幫助文檔還沒有負責人，就需要再找人認領。

## 把需要跟進的事安排好

不是每一個行動項都需要提醒。先挑出確實有時間要求、又容易忘的事項，再在對話里提出具體要求：

> 週五上午十點提醒我向小林確認搜索測試結果，到點通知我。

在 iOS 授權了[提醒事項]({{ "/zh-Hant/guide/device-data/" | relative_url }})後，檢查彈出的事項、日期、時間和通知設定，確認後再創建。只寫到期時間，並不等於一定會在那個時間通知你。

錄音過程中如果出現了可選操作，也要先查看再確認。出現建議或完成錄音，都不會自動執行這些安排。

## 下次再聊，接著這次往下走

後續有人補充了報價、修改了日期，或完成了一項任務，就把新材料繼續放進同一主題。下次討論前，先看主題的最近變化和開放問題，再決定這次重點談什麼。

訪談也可以這樣整理，只是提問要換一下：例如「按受訪者的觀點整理，每個觀點保留一段原話，標出還需要追問的地方」。

錄音中的即時整理需要 API Key；使用 Codex 登入時，也可以先錄音，儲存後再轉寫和整理。
